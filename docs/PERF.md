# Замеры производительности

Как мерили: adb на Galaxy S23 Ultra (120 Гц), Wi-Fi, телефон подключён по USB. Команды:
- запуск: `am start -W`;
- плавность прокрутки: `dumpsys gfxinfo` (доля подтормаживающих кадров, перцентили времени кадра);
- память: `dumpsys meminfo` (PSS, native heap);
- процессор: `top`, в процентах одного ядра;
- время до первого звука: от нажатия до состояния PLAYING.

⚠ Разобрано, это не регресс. Время старта трека не из кэша почти целиком уходит на B2:
- Сервер файлов `f004.backblazeb2.com` стоит в США: до него ≈220 мс в одну сторону, TCP и TLS ≈0,5 с.
- Ответ на запрос файла приходит через 1,0–2,0 с. Это строка `B2P/net: Open … ms` в подробном логе.
- Дальше 0,8–0,9 с уходит на первые ≈300 КБ: у MP3 в теге ID3 лежит обложка на ≈240 КБ, и на таком расстоянии TCP разгоняется медленно.

Итого 1,8–2,3 с. Начинать играть после 1 с звука вместо 2,5 с не помогло (2,3 с против 1,85 с, в пределах разброса), правку откатил. 0,44 с в первом замере — скорее всего трек, заранее подгруженный предзагрузкой. Следующие треки очереди начинаются за 0,16–0,3 с, потому что подгружаются заранее.

Сократить сам первый запрос можно только сервером ближе: Cloudflare перед бакетом или аккаунт B2 в регионе EU.

Как перемерить: включить Settings → Diagnostics → Detailed logs, перезапустить приложение и смотреть `adb logcat -s 'B2P/*'`. В строке `B2P/net: Open … ms` — ответ B2, в строке `B2P/player: Sound after … ms` — время от смены трека до звука.

## 2026-11-20, старт шаффла и обложки в очереди

Как мерили: эмулятор b2test на маке (sdk_gphone64_arm64), release-сборки ветки до исправления (b00986d, это main #120 и строки лога «Queue items in» и «Sound after» для новой очереди) и после (0900ce7). Detailed logs включены. Library с фильтром лайкнутых → Tracks → Shuffle по 2523 лайкнутым трекам; время от строки `Play N tracks` до `Queue items in` (собрана очередь), `Now … (reason 3)` (очередь дошла до плеера) и `Sound after`. В эмуляторе скачано только 18 треков, остальные идут из кэша или B2. «Плохая сеть» — `iptables -I OUTPUT -p tcp --dport 443 -j DROP`: соединения висят до таймаута, как на слабой сети; перед ней удалён кэш обложек и пролистан список лайкнутых. Мак был нагружен (Spotlight, load average 12–18), эмулятор несколько раз уходил в системный ANR, поэтому первые запуски после старта (11–31 с, проверка каталога тогда шла до 50 с) в таблицу не вошли.

| Проверка | Было | Стало |
|---|---|---|
| Нормальная сеть: очередь собрана | 0,8–1,6 с | 1,5–1,6 с |
| Нормальная сеть: звук | 3,0–3,5 с, один раз не наступил (36 с буферизации) | 1,8–2,0 с, первым играет скачанный трек (4 из 5) |
| Плохая сеть после прокрутки: очередь собрана | 1,7 / 16,6 / 13,4 с | 1,6 с |

Причины. Обложки качались в общем пуле Dispatchers.IO без ограничения: на плохой сети дамп потоков показал 34 из 68 потоков, висящих в `Covers.load → B2.download → Socket.connect` (таймаут 15 + 30 с), а очередь для Play и Shuffle собирается в том же пуле и ждала их. Теперь обложки качаются на своих 4 потоках. Обложки хранились только для уже показанных альбомов, поэтому у скачанных треков без сети их не было: теперь обложки альбомов с лайками докачиваются после загрузки каталога и после изменения лайков. Шаффл начинал со случайного трека, часто нескачанного; теперь со скачанного, если он есть в списке.

Не исправлено: сборка очереди сама по себе ≈1,5 с на 2500 треков в эмуляторе (проверка файла загрузки на каждый трек, а с LITE ещё и кэша). На телефоне не мерили: он не был подключён.

## 2026-11-21, шаффл всей библиотеки

Как мерили: эмулятор b2test на маке (sdk_gphone64_arm64, Android 15, лимит Java heap 192 МБ), release-сборки main (9fd364e) и ветки с правкой. Detailed logs включены. Library с фильтром All → Tracks → Shuffle по 17966 трекам; время от строки `Play N tracks` до `Queue items in` (собрана очередь), `Now … (reason 3)` (очередь дошла до плеера) и `Sound after`. Перед каждым замером приложение запускалось заново, кроме строк «подряд». В эмуляторе скачано 6 треков, шаффл начинает с одного из них. «Плохая сеть» — `iptables` и `ip6tables -I OUTPUT -p tcp --dport 443 -j DROP`. Java heap — `dumpsys meminfo` после принудительного GC (`kill -10`).

| Нормальная сеть: звук от `Play` | 4,8–6,1 с | 1,1–1,4 с |

| Java heap: после старта / после 1, 2, 4 шаффлов | 70 / 113 / 145–149 МБ / OOM | 53 / 63 / 64 / 63 МБ |

Причины. Дампы потоков (`kill -3`): пока собиралась очередь, 15 из 16 снимков — `Library.mediaItem → File.exists` на каждый трек, ≈0,25 мс на вызов в общей памяти, хотя `ls -R` всей папки загрузок занимает 0,02 с. Теперь файлы ищутся по списку файлов папки альбома, один `list()` на папку. Пока очередь передавалась плееру, главный поток в `ExoPlayerImpl.setMediaItems → Util.inferContentType` раскодировал путь каждого трека; теперь у элемента очереди задан MIME-тип, и угадывать не нужно. Память: дамп heap показал, что старые очереди целиком держит `DefaultAnalyticsCollector` ExoPlayer — он хранит последнее событие каждого вида со временной шкалой того момента, и событие «включён шаффл» держало очередь, бывшую до первого шаффла, остальные — предыдущую; ≈40 МБ на очередь всей библиотеки. Аналитику ExoPlayer никто в приложении не слушает, теперь вместо неё пустая заглушка. Заодно из элемента очереди убран неиспользуемый Bundle с путём.

Не исправлено: с LITE на каждый трек ещё проверяется кэш (`isCached`, блокировка кэша), в замере это не заметно. Значок «скачано» в строке списка проверяет файл на главном потоке, по одному на видимую строку. На телефоне не мерили: он не был подключён; там скачаны тысячи треков, но число `list()` равно числу папок альбомов в очереди, а не числу файлов.

### Узкие места

1. Фильтр очереди Not liked и All: кадр 280–550 мс. `PlaybackService.placeInShuffle` делает `order.filter { it !in added }`, где `added` — список: 18k × 15k сравнений на главном потоке.
2. Каждая смена трека при большой очереди: кадр 60–190 мс. `Ui.sync` на каждое событие плеера заново собирает `queueIds` (18k `getMediaItemAt`) и `playOrder` (`getNextWindowIndex`); ≈39% главного потока. Скорее всего, отсюда же перетаскивание в очереди и первое её открытие.
3. Downloads, «Counting…» 9–12 с: `isDownloaded` (`File.exists`) на каждый из 18k треков, вместо `downloadedCheck()`.
4. Фильтр «Search in this list», сортировки и периоды: 50–180 мс на главном потоке. `Query.rank` режет ключ каждого трека регуляркой на каждую букву (`Regex.split` 54%).
5. Local Binders +1 и native heap +0,4 МБ за смену трека. 55 из 103 binder-узлов держит `com.google.android.googlequicksearchbox:interactor`; на телефоне проверить.
6. Сборка очереди 18k 0,6–0,7 с: `Uri.encode` в `uriFor` ≈36%, `list()` по папкам альбомов, в том числе несуществующим, ≈33%.
7. Переключение LITE 1–2 с: `switchFiles` пересобирает все элементы через `mediaItem`.
8. На переднем плане новое TLS-соединение каждые 15,7 с для проверки, что играет на другом устройстве.

Не замерено: «Playing on Mac» (cmus не играл), звук после переключения LITE, телефон (не подключался).
